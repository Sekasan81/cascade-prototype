# Идея: специализированные порталы для заданий

СТАТУС: рабочая концепция будущей версии. Не внедрено в игру. Механика может изменяться и дополняться по мере дальнейшей разработки.

Сводные правила состава группы, прогресса, генерации и наград контрактов описаны в `quest-system.txt`. Этот файл подробнее рассматривает фильтрацию и работу специализированных порталов.

## Основная схема

При генерации задания ему назначается открытое целевое направление и набор условий, по которым определяется, каких пассажиров необходимо отправить. Контракты для закрытых направлений не генерируются.

После принятия задания на станции появляется отдельный портал, связанный именно с этим заданием. Для каждого контракта создаётся свой портал вместимостью на всю требуемую группу. Например, для шести литоидов-гигантов по 6 мест нужна вместимость 36 мест. Квестовый портал не открывает этих пассажиров для обычной генерации.

Портал получает условия задания и имеет жёсткую автоматическую фильтрацию: он пропускает только пассажиров, которые соответствуют всем требованиям, включая дополнительные фильтры. Все такие фильтры заранее доступны игроку в раскрываемом списке полных требований карточки контракта.

Таким образом, игрок физически не может отправить через квестовый портал пассажира, который не подходит под условия задания.

## Пример

Задание:

> 🪐 Марс требует 5 инсектоидов для работы в горнодобывающей колонии.

При генерации задания могут быть заданы условия:

- 🐜 раса: Инсектоиды;
- ⛏️ профессия: Шахтёр;
- 👷 статус: Рабочий;
- 🔢 количество: 5.

После принятия появляется:

> 🌀 Марс — Горнодобывающая колония

Портал проверяет характеристики каждого отправляемого пассажира.

Подходящий пассажир:

> 🐜 Инсектоид + ⛏️ Шахтёр + 👷 Рабочий → ✅ пропускается.

Неподходящий пассажир:

> 🐜 Инсектоид + 💼 Торговец + 👷 Рабочий → ❌ не пропускается.

Другой пример:

> 💎 Инсектоид + ⛏️ Шахтёр + 👑 VIP → ❌ не пропускается, если статус/другие условия задания не соответствуют.

## Почему это важно

У каждого пассажира есть набор допустимых направлений. Контракт задаёт целевое направление своего портала; портал пропускает пассажира только если цель контракта входит в допустимый набор пассажира и пассажир удовлетворяет остальным условиям контракта.

Это позволяет одновременно учитывать ограничения пассажира по направлениям и требования контракта. Подходящий по расе VIP-пассажир не становится кандидатом для рабочего контракта, если не проходит его прочие условия.

Например, если Марсу нужны инсектоиды-шахтёры, наличие инсектоида само по себе недостаточно — портал пропустит только пассажира, соответствующего полному набору требований.

## Возможные условия портала

На первом этапе предполагается использовать:

- расу;
- профессию;
- статус пассажира.

В дальнейшем список условий можно расширять, например:

- размер;
- состоятельность;
- черты;
- дополнительные особенности;
- багаж;
- другие характеристики пассажира.

## Завершение задания

Игрок пропускает подходящих пассажиров через соответствующий портал.

Каждый успешно отправленный пассажир увеличивает прогресс задания.

Счётчик увеличивается только после успешного завершения отправки пассажира через портал этого контракта. Назначение на портал и запуск подготовки сами по себе прогресс не засчитывают. Пассажир, подходящий требованиям нескольких активных контрактов, может быть назначен игроком только на один из их порталов и засчитывается только этому контракту. Он не может одновременно увеличить прогресс двух контрактов. Генератор создаёт только пассажиров, необходимых для оставшегося требования. Если пассажир улетает без отправки, он не засчитывается и заменяется; на прогрессе 5/6 создаётся только один недостающий пассажир, а не новая группа из шести.

Когда достигнуто требуемое количество (например, 6/6), генерация пассажиров для контракта прекращается. Игрок вручную закрывает выполненный контракт в меню контрактов; связанный портал удаляется при закрытии. Игрок может отправлять группу целиком или несколькими партиями, повторно используя портал контракта.

## Возможная схема

**Генерация задания → условия задания → принятие задания → появление специализированного портала → проверка пассажира → пропуск только при полном соответствии → прогресс задания → выполнение → закрытие портала.**

## Отмена контракта и квестовые пассажиры

Квестовый пассажир может подходить требованиям нескольких контрактов и остаётся общим кандидатом до назначения на портал. При отмене одного контракта пассажир сохраняется, если подходит хотя бы одному другому активному контракту; если он больше не нужен ни одному контракту и был создан только для отменённого, его удаляют. После назначения на портал пассажир закрепляется за выбранным контрактом. Отмена сразу закрывает портал отменённого контракта; выделенный пассажирам ресурс не возвращается. Пока портал готовится или выполняет отправку, отмена контракта заблокирована. После завершения отправки отмена снова доступна, если контракт ещё не выполнен.

## Несколько активных заданий

На станции потенциально может одновременно существовать несколько квестовых порталов с разными требованиями.

Например:

- 🌀 Марс — шахтёры;
- 🌀 Венера — туристы;
- 🌀 Альфа — дипломаты.

Один и тот же пассажир может подходить нескольким порталам, если соответствует условиям нескольких контрактов. Игрок выбирает, на какой портал его назначить. Пассажир засчитывается только одному контракту — тому, чей портал был выбран; повторно засчитать его в другой контракт нельзя. При расчёте генерации один пассажир также покрывает потребность только одного контракта: доступных кандидатов распределяют по самым узким требованиям, чтобы подходящий сразу нескольким контрактам пассажир не был учтён дважды. До назначения пассажир остаётся доступен для выбора игрока.

## Пока не определено

Пока остаются открытыми:

- точный набор условий;
- отдельные ограничения направлений для профессий, архетипов и особенностей, если они понадобятся; для рас действует общее правило: доступны все открытые направления;
- правила генерации условий;
- максимальное количество одновременно активных порталов;
- внешний вид и расположение порталов;
- UI требований портала;
- что происходит с пассажирами, которые не подходят ни под один активный портал;
- дополнительные правила после выполнения задания.

Эта концепция является рабочей основой и может пересматриваться в процессе дальнейшей разработки.
